# ④ 権限・ロール設計 v1

現状のプロトタイプは「1社＝1ユーザー」前提になっている。実際の会社には社長・現場担当・
経理がいて、それぞれ見せたいもの・触らせたくないものが違う。ここを設計しないと、
5人以上の会社では導入できない。

---

## 0. 前提となる実態

| 規模 | 実態 | 必要なこと |
|---|---|---|
| **一人親方** | 全部ひとりでやる | ロール分けは不要。既定で全権限 |
| **3〜10人** | 社長が営業と契約、奥さんか事務員が請求、職長が現場 | **経理と現場を分けたい**。金額を職人に見せたくない |
| **10〜30人** | 現場ごとに職長、事務は専任、社長は決裁のみ | 現場担当が自分の現場だけ触れる状態が必要 |
| **30人〜** | 部門がある | 承認フローが要る（本設計では対象外・将来） |

**最も切実なのは「金額を現場に見せない」**。職人に請負金額が見えると、
人工単価との差額が分かってしまい、社内で問題になる。ここは日本の建設業でかなり強い要求。

---

## 1. ロール定義

| ロール | 想定 | 一言 |
|---|---|---|
| `owner` | 代表者 | 全権限。会社に必ず1名。譲渡のみ可、削除不可 |
| `admin` | 番頭・専務 | owner とほぼ同じ。ユーザー管理とプラン変更のみ不可 |
| `accounting` | 事務・経理 | 金額と書類を扱う。現場の写真・日報は閲覧のみ |
| `field` | 職長・現場担当 | **金額が見えない**。日報と写真、割り当てられた現場のみ |
| `viewer` | 閲覧のみ | 監査・外部の会計事務所など |

## 3. 現場担当の「担当のみ」の実装

```sql
create table site_assignments (
  transaction_id uuid not null references transactions(id) on delete cascade,
  user_id        uuid not null references users(id) on delete cascade,
  assigned_at    timestamptz not null default now(),
  primary key (transaction_id, user_id)
);
```

- `field` ロールのユーザーは、`site_assignments` にある取引だけが見える
- 割り当ては owner / admin / accounting が行う
- 未割り当ての `field` ユーザーには「担当の現場がありません」と表示する

```sql
create policy tx_field_scope on transactions for select using (
  case (select role from users where id = auth.uid())
    when 'field' then exists (
      select 1 from site_assignments sa
      where sa.transaction_id = transactions.id and sa.user_id = auth.uid()
    )
    else moto_company = my_company() or uke_company = my_company()
  end
);
```

## 4. 金額の秘匿

`field` ロールに対しては、以下を**UIから完全に消す**（マスクではなく非表示）。

- 注文書の請負代金・人工単価
- 請求書の全項目
- 取引一覧の「請負総額」「請求済」「残り」
- 会社ページの取引実績・支払実績
- 案件の指値・人工単価

**日報の人数は見える**。これがないと日報が書けない。

```ts
// Server Action 側で必ず落とす。クライアントに送ってからCSSで隠すのは不可
const canSeeAmount = (role: Role) => role !== "field";

export async function getTransaction(id: string) {
  const me = await currentUser();
  const tx = await load(id);
  if (!canSeeAmount(me.role)) {
    return stripAmounts(tx);   // orders[].amount, invoices 全体を除去
  }
  return tx;
}
```

## 5. ユーザーの追加

### 招待フロー

1. owner が「メンバーを招待」→ 氏名・ロール・連絡先（SMS またはメール）を入力
2. 招待リンクを送信（有効期限7日）
3. 相手が開いてパスワードを設定 → 同じ `company_id` に紐づく
4. owner に「{名前}が参加しました」を通知

### プランとの関係

| プラン | ユーザー数 |
|---|---|
| 無料 | 1名 |
| スタンダード | 3名 |
| プロ | 10名 |
| プレミアム | 無制限 |

> これは**新しく決める必要がある項目**です。人数制限を入れるかどうかは判断が要ります。
>
> **入れる場合の利点**：会社の規模と料金が連動する。大きい会社ほど払う
> **入れない場合の利点**：現場に日報を書かせたいのに人数で詰まる、が起きない。日報が増えるほどデータの価値が上がる
>
> 私の意見としては、**`field` ロールだけ人数無制限**にするのを勧めます。
> 日報を書く人が増えるほどプラットフォームのデータは厚くなるので、そこは絞らない方がいい。
> 金額を扱える `owner`/`admin`/`accounting` の合計だけ制限するのが筋が通ります。

## 6. 監査ログ

信用情報を扱う以上、「誰がいつ何をしたか」は残す必要がある。

```sql
create table audit_logs (
  id          bigserial primary key,
  company_id  uuid not null,
  user_id     uuid,
  action      text not null,      -- 'order.issue' 'invoice.approve' ...
  entity      text not null,      -- 'orders' 'invoices' ...
  entity_id   uuid,
  before      jsonb,
  after       jsonb,
  ip          inet,
  created_at  timestamptz not null default now()
);
create index on audit_logs (company_id, created_at desc);
create index on audit_logs (entity, entity_id);
```

**必ず記録する操作**
- 注文書の発行・請書の返送・差し戻し
- 請求の提出・承認・支払登録・入金確認
- 異議申立と運営の判断
- ロールの変更、ユーザーの追加・削除
- 信用書類の提出・承認・差し戻し

異議申立の事実確認で、この監査ログが決定的な証拠になる。

## 7. 実装の優先度

| 優先 | 内容 | 理由 |
|---|---|---|
| **高** | ロールの区分と金額の秘匿 | これがないと3人以上の会社が使えない |
| **高** | 監査ログ | 後から入れるとデータが欠ける |
| 中 | 現場の担当割り当て | 10人規模から必要になる |
| 中 | 請求承認の金額上限 | 経理に任せる会社で必要 |
| 低 | 承認フロー（多段階） | 30人規模から。当面は不要 |

P0（認証・会社登録）の時点でロールを入れておくこと。後から追加すると、
既存ユーザー全員のロール設定をやり直すことになる。
