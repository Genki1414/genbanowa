## 0. これは何か

**ゲンバノワ** — 建設業の下請案件マッチング＋受発注SaaS。
運営は東北三上機材株式会社（宮城県名取市・足場工事業）。

一行で言うと：

> 仕事が見つかって、取った後の書類まで全部ここで終わる。

**ツクリンクや助太刀が「探すところまで」で終わっているのに対し、
取ったあとの注文書・請求書・日報・工事写真まで一本にするのが差別化点。**

## 2. 技術スタック（確定）

```
Next.js (App Router) + TypeScript
Supabase (Postgres / Auth / Storage / RLS)
Vercel
Tailwind CSS
```

- 状態管理ライブラリは入れない。Server Components + Server Actions
- ORM は使わない。Supabase クライアント + 型生成
- テストは vitest（ドメイン層のみ。UIテストは当面書かない）

**既存資産**：別プロジェクト `ashibaya-line` に TypeScript DDD のドメイン層があります。
`Transaction` 集約・`BillingTrack`・`availableActions(role)` は流用します。
対応表は `01_実装設計書.md` の第4章を参照。

## 3. 最初にやること（この順番で）

### Step 1. 骨組み

```bash
npx create-next-app@latest genbanowa --typescript --tailwind --app --src-dir
```

`src/` の構成は `08_リファクタ分割設計.md` の第1章に従ってください。

### Step 2. デザイントークンを移植

`deploy/style.css` の `:root` と、`.jsx` 冒頭の `C` オブジェクトが同じ値です。
`src/styles/tokens.ts` に置いて、**ここ以外に色を書かない**こと。

```ts
export const C = {
  sumi:   "#14171C",  // 墨 — 文字・ヘッダ
  kami:   "#FFFFFF",  // 紙 — カード
  yojo:   "#E9EDEA",  // 養生 — 下地
  keisen: "#D6DBD7",  // 罫線
  ki:     "#F5C518",  // 安全黄 — 進行中・アクセント
  midori: "#00874A",  // 安全緑 — 完了・良好
  aka:    "#D22630",  // 安全赤 — 対応待ち・警告
  usu:    "#6B7280",  // 副文字・終了
} as const;

export const TONE = {
  action: C.aka,     // あなたの対応待ち
  active: C.ki,      // 進行中
  done:   C.midori,  // 完了・良好
  off:    C.usu,     // 終了・停止
} as const;
```

**色の意味は固定です。** アプリ内に凡例を出しているので、実装が揺れると嘘になります。

### Step 3. UI部品を切り出す

`.jsx` にある以下をそのまま `src/components/ui/` へ。

`DenpyoCard` `Chip` `Row` `Btn` `Field` `DateRange` `Pills` `Radio`
`Header` `Confirm` `Legend` `Gate` `Locked` `MineHead` `Stars`

**`DenpyoCard` は絶対に残してください。** 左端のミシン目が
「これは伝票です」という合図になっていて、業界の人に一発で伝わります。

### Step 4. ドメイン層と権限を先に作る

**UIより先です。** `checkQuota()` と `can()` の2つを作って、
以降の判定を全部そこに寄せます。

```ts
// src/domain/plan/Quota.ts
export function checkQuota(plan, usage, key):
  { ok: true } | { ok: false; reason: string; limit: number | "unlimited" }

// src/domain/auth/Permission.ts
export function can(role: Role, action: Action): boolean
```

理由：プロトタイプでは判定がUIに30箇所以上散っています。
特に `field`（現場担当）ロールの**金額秘匿は漏れると信用事故**になるので、
1箇所に集約してから実装してください。

### Step 5. DBを作る

`01_実装設計書.md` の第1章のSQLをそのまま流します。
**`companies.unlocked_features` と `stance` を忘れないこと**（段階開放用・後から足すと既存ユーザーの埋め直しが発生）。

### Step 6. P1（取引）から実装

実装順は `01_実装設計書.md` 第6章。**P1単体で受発注ツールとして売れる状態**を目指します。

## 4. 絶対に守ること

### 4-1. 金額の秘匿はサーバー側で落とす

```ts
// ✕ クライアントに送ってからCSSで隠す
// ○ Server Action で stripAmounts() してから返す
```

`field` ロールに見せないもの：注文書の金額、請求書の全項目、
取引一覧の金額、会社の取引実績・支払実績、案件の指値・人工単価。
**日報の人数だけは見せます**（ないと日報が書けない）。

### 4-2. 段階開放は取り消さない

`unlocked_features` への追加のみ。削除する処理を書かないでください。
プランを下げても、`stance` を変えても、一度出た機能は消えません。

ナビに出ていない画面のURLに直接来た場合は、**404にせず解放して表示**します
（通知のリンクから飛んでくるため）。

### 4-3. 遅延は確定するまで記録しない

`invoices.received_on > due_date` でも、それだけでは遅延になりません。
`payment_disputes` を通って `status='recorded'` になったものだけが
信用情報に載ります。判定基準は `03_規約・信用情報方針ドラフト.md` 第4-4条。

**期日内入金は取引ごとに何度でもカウント**します。

### 4-4. 書類は送信後に変更できない

注文書・注文請書・請求書は immutable。訂正は差し戻しか、新しい書類の発行で行います。
PDFは生成時に保存し、再生成しません（原本性の確保）。

### 4-5. 取引はメッセージからしか始まらない

「この会社に取引を依頼する」は会話の中にしか置きません。
案件のやり取りからでも、会社一覧から直接送ったやり取りからでも始められますが、
**取引タブから単独で注文書を作ることはできません。**

### 4-6. 1枚の請求書に複数の注文書は載せない

追加工事は2枚目以降の注文書として発行し、請求書は注文書を1枚だけ指定します。
注文書の金額を超える請求は**警告は出すが拒否しない**（追加分を先に請求するケースがあるため）。

## 5. プラン定義（そのままコードに入れてよい）

```ts
const INF = Infinity;
export const PLANS = {
  free: { name:"無料",         price:0,     detail:3,   send:1,  recv:"pt", scout:1,  post:1,   aki:1,   site:2,   gb:1,   users:1,   docs:false, info:0 },
  std:  { name:"スタンダード", price:2980,  detail:INF, send:5,  recv:INF,  scout:5,  post:INF, aki:3,   site:5,   gb:10,  users:3,   docs:true,  info:1 },
  pro:  { name:"プロ",         price:5000,  detail:INF, send:15, recv:INF,  scout:15, post:INF, aki:6,   site:15,  gb:50,  users:10,  docs:true,  info:2 },
  prem: { name:"プレミアム",   price:10000, detail:INF, send:40, recv:INF,  scout:40, post:INF, aki:INF, site:INF, gb:INF, users:INF, docs:true,  info:3 },
};
```

| key | 意味 |
|---|---|
| `detail` | 案件詳細の閲覧（月）。同じ案件の再閲覧は消費しない |
| `send` | やり取りできる案件数。**その月に新規開始した会話数**で数える |
| `recv` | スカウトの閲覧。`"pt"` は閲覧ポイント制（無料のみ・月次リセットなし） |
| `scout` | スカウト送信（月） |
| `post` | 案件投稿（月） |
| `aki` | 掲載中の空き情報の件数（同時） |
| `site` | 現場フォルダの件数（同時・アーカイブ除く） |
| `gb` | 写真の保存容量 |
| `users` | **金額を扱えるユーザー数**。`field` ロールは無制限 |
| `docs` | 書類の発行可否 |
| `info` | 会社情報の開示レベル 0=基本 1=取引実績 2=+運営評価/HP 3=+支払実績 |

**数値は変更前提です。** `plan_limits` テーブルで持って、コードにハードコードしないでください。
根拠は `05_プラン上限シミュレーション.md`。リリース後1か月のログで必ず調整します。
