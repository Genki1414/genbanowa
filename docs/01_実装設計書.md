# ① 本番実装 設計書 v1

Next.js (App Router) + Supabase + Vercel。既存の信用プラットフォーム（ashibaya-line）のドメイン層を流用する。

---

## 0. 全体方針

| 層 | 方針 |
|---|---|
| UI | Server Components 中心。フォーム送信は Server Actions |
| ドメイン | `src/domain/` の既存 TypeScript DDD を移植。UIから直接DBを触らない |
| 永続化 | 集約は JSONB スナップショット＋非正規化フィルタ列（既存方針を踏襲） |
| 認可 | Supabase RLS を第一防壁。特権処理は SECURITY DEFINER 関数 |
| 冪等性 | 状態遷移・信用スコア更新は必ず冪等キー付き |

**足場依存の除去**：既存ドメインの `WorkTrack`（組立／解体）は本アプリでは使わない。代わりに `DailyReport`（作業日報）を進捗の単位とする。`BillingTrack` と `Transaction` 集約はほぼそのまま流用できる。

**遅延カウントの原則**
- `invoices.received_on <= due_date` → 期日内。取引ごとに何度でもカウント
- `received_on > due_date` → **即座には遅延にしない**。`payment_disputes` を通り `status='recorded'` になったものだけを遅延として集計

```sql
create view company_payment_stats as
select
  t.moto_company as company_id,
  count(*) filter (where i.received_on <= i.due_date) as ontime_count,
  count(*) filter (where d.status = 'recorded')       as delay_count
from invoices i
join transactions t on t.id = i.transaction_id
left join payment_disputes d on d.invoice_id = i.id
where i.status = 'received' or d.status = 'recorded'
group by t.moto_company;
```

### 1-10. 段階開放（画面の出し分け）

多機能であることが初回の障壁にならないよう、機能は**使う理由が生まれた時点で解放**する。

**保存場所は `companies.unlocked_features`（会社単位）。**
ユーザー単位にすると、後から参加した現場担当の画面だけが初期状態に戻ってしまう。
会社として一度使った機能は、新しいメンバーにも最初から見えているべき。

| 機能 | 初期 | 解放条件 |
|---|---|---|
| 案件をさがす | ○ | — |
| メッセージ | ○ | — |
| 自社 | ○ | — |
| 会社をさがす | × | 案件を投稿する／スカウトを開く／`stance` が `moto`・`both` |
| 取引 | × | 注文書を送る（取引が1件立つ） |
| 工事写真 | × | 注文請書を返す |

```sql
-- 解放は追加のみ。取り消す処理は作らない
create or replace function unlock_feature(p_company uuid, p_key text)
returns void language sql security definer as $$
  update companies
     set unlocked_features = array(select distinct unnest(unlocked_features || p_key))
   where id = p_company;
$$;
```

**実装上の注意**

1. **解放は冪等**にする。同じキーを何度呼んでも増えない
2. **取り消し処理を実装しない**。`stance` を戻しても、プランを下げても隠さない
3. 解放時はアプリ内で通知する（`FEATURE_UNLOCKED`）。「増えた」と気づかせることが目的
4. 自社ページに**未解放の機能と条件を一覧表示**する。隠すのではなく「これから使える」と見せる
5. ナビに出ていない画面のURLに直接来た場合は、**404にせず解放して表示**する。

## 2. RLS 方針

```sql
alter table companies enable row level security;

-- 自社は全部見える
create policy own_company on companies for select
  using (id = (select company_id from users where id = auth.uid()));

-- 他社は「一覧に出る範囲」のみ。列制限はビューで行う
create view companies_public as

       industries, service_areas, license_no, trust_score, trust_level

```

**プラン依存の開示はビューを分ける**（RLSで列制御はできないため）

| ビュー | 開示内容 | 必要プラン |
|---|---|---|
| `companies_public` | 基本情報・信用スコア・提出書類の有無 | 全員 |
| `companies_stats` | 発注数・受注数・取引社数 | std 以上 |
| `companies_rating` | 運営の星評価 | pro 以上 |
| `companies_payment` | 期日内支払数・遅延数 | prem 以上 |
| `companies_url` | HP・SNS の URL | pro 以上 |

各ビューは Server Action 側でプランを検査してから読む。RLS だけに頼らず、**アプリ層でも二重に検査する**。

```sql
-- 取引は当事者のみ
create policy tx_parties on transactions for select using (
  moto_company = my_company() or uke_company = my_company()
);
-- 書き込みは当事者かつ、役割に応じた操作のみ（詳細は権限設計書）
```

**特権処理（SECURITY DEFINER）**
- `recalc_trust_score(company_id)` — 信用スコアの再計算
- `record_payment_delay(dispute_id, decision)` — 遅延の確定記録（運営のみ）
- `consume_invite_point(company_id, scout_id)` — 閲覧ポイントの消費（冪等）

いずれも `idempotency_key` を受け取り、二重実行を防ぐ。

## 4. 既存ドメイン層の対応表

| ashibaya-line の資産 | 本アプリでの扱い |

## 7. 決めきれていない点

- **PDF生成の場所**：Server Action 内で生成するか、Edge Function に切るか。日本語フォントの埋め込みサイズ次第
- **写真の元画像保持**：公共対応を将来やるなら raw を残すべきだが、ストレージ費用が読めない。まず90日保持で様子を見る
- **conversations の一意制約**：同じ相手と同じ案件で複数スレッドを許すか。今は禁止しているが、現場ごとに分けたい要望が出る可能性
- **やり取り枠の数え方**：「その月に新規開始した会話数」としたが、翌月に持ち越した会話が枠を占有し続けるべきかは要検討
