# ⑫ P1 動作確認チェックリスト v1

`docs/11_シードデータ.md` 末尾の「動作確認シナリオ」のうち、P1（取引）に関わる5本を対象にする。
1操作＝1行。各シナリオの最後に合格条件を明記した。

現状の実装範囲の注記：**画面のタブナビゲーション（案件・会社・取引・工事写真の出し分け）はまだ存在しない**
（P2〜P5未実装のため）。段階開放そのもの（`companies.unlocked_features`への追加）は一部動くが、
それを反映するタブUIがないので、シナリオ1は限定的にしか検証できない。詳細はシナリオ1の節を参照。

## 0. テストアカウントの準備

シードの取引はシードの会社（高橋工業・京葉建設工業・彩北総業・丸和塗装）に紐づいている。
実際にサインアップすると `bootstrap_company()` が毎回新しい会社を作ってしまうため、
そのままではRLSでシードの取引が1件も見えない。`supabase/dev/link_test_account.sql` で
サインアップ後のユーザーをシードの会社へ付け替える。

必要なアカウントは3つ。

| アカウント | 会社 | ロール | 用途 |
|---|---|---|---|
| A | 高橋工業 | owner | シナリオ1・3・4、シナリオ2の割り当て操作 |
| B | 高橋工業 | field（Aが招待） | シナリオ2の閲覧確認 |
| C | 丸和塗装 | owner | シナリオ5（取引3の請求は丸和塗装＝受注側の操作のため） |

### 手順

1. `/signup` でアカウントAを作成 → `/signup/company` で適当な会社名（例：テスト会社）を登録
   （この時点では自動生成された別会社になる。次のSQLで高橋工業に付け替える）
2. Supabase Dashboard → SQL Editor で `supabase/dev/link_test_account.sql` を開き、
   `v_email` をAのメールアドレスに書き換えて実行 → 出力の `company_name` が `高橋工業` になっていること
3. アカウントAで `/login` → `/transactions` → シードの取引3件（五井中央／川口栄町／浦安）が
   一覧に出ることを確認
4. アカウントAで `/me/members` を開き、氏名・別メールアドレス（アカウントB用）・
   ロール「現場担当」で招待 → 届いた招待メールのリンクからパスワードを設定
   （招待経由なので `link_test_account.sql` は不要。トリガで自動的に高橋工業のfieldになる）
5. 同様に `/signup` でアカウントCを作成 → `link_test_account.sql` の `v_company_name` を
   `丸和塗装` に書き換えてCのメールで実行

## シナリオ1｜段階開放（限定的に検証）

**現状UIから再現できない部分**：会話から取引を依頼する画面（P2）がまだないため、
`createTransactionAction`（新規取引＝新規会話から注文書を送る）はUIから呼び出せない。
「取引タブが解放される」の検証はP2実装後に回す。

**今回検証できる部分**：注文請書を返すと工事写真タブが解放される、の裏側（`unlocked_features`への追加）。

1. Supabase Dashboard → Table Editor → `companies` で高橋工業の行を開き、
   `unlocked_features` に `photos` が含まれていないことを確認（含まれていたら別シナリオで
   既に付いている可能性があるので、`彩北総業`など請書未返送の取引の相手側で試す）
2. アカウントAで、取引2（川口栄町・請書待ち）の詳細画面から何もせず戻る
3. 同じ `companies` テーブルで高橋工業の `unlocked_features` を再確認 → まだ `photos` は付かない
4. シナリオ3の手順で取引1のNo.2の請書を返す（後述）
5. 再度 `companies` テーブルを確認 → `unlocked_features` に `photos` が追加されていること

**合格条件**：請書を返す前は`photos`が無く、返した後に追加されている。

## シナリオ2｜金額の秘匿（最重要：ネットワークタブで確認）

1. アカウントAで `/transactions/取引1のID` を開く
2. 「現場担当の割り当て」セクションでアカウントBの名前チップをクリックして担当に設定
   （チップが緑色＝「（担当）」表記になる）
3. ログアウトし、アカウントBでログイン
4. `/transactions` を開く → **割り当てた取引1件だけ**が表示されること（他の2件は出ない）
5. その取引の詳細を開く → 注文書・請求のどこにも金額（¥のついた数字）が出ないこと。
   作業日報の「人数」は表示されていること
6. ブラウザの DevTools → Network タブを開いた状態で `/transactions/取引1のID` を再読み込みする
7. Network タブで、そのページ自体のリクエスト（Document、または `_rsc` の付いたリクエスト）の
   レスポンス本文を検索し、`1860000` や `1200000` のような金額の生数値が**一切含まれていない**ことを確認

**なぜこれで良いか**：この画面はNext.jsのServer Componentで、`stripAmounts(role)`を
サーバー側で実行してから描画している。金額を表示するUI部品（OrderCard・InvoiceCard等）も
すべてServer Component（`"use client"`が付いていない）なので、レンダリング結果に出てこない値は
そもそもクライアントに送られるHTML/RSCペイロードに含まれ得ない。CSSで隠しているだけなら
Networkタブのレスポンスに生の金額が写り込むので、それが無いことが「サーバー側で落ちている」証拠になる。

**合格条件**：
- 画面上に金額が一切表示されない（日報の人数は表示される）
- Networkタブのレスポンスにも金額の生数値が含まれない
- 未割り当ての取引は一覧にすら出ない

## シナリオ3｜追加工事（請書を返すと請求できるようになる）

1. アカウントAで `/transactions/取引1のID`（五井中央）を開く
2. 注文書 No.2（追加：north面のハネ出し、請書待ち＝aka色）を確認
3. 「請書を返す」→確認モーダル→送信
4. 画面が更新され、No.2が「請書返送済」（緑）になっていることを確認
5. 「+ 請求書を作る」から `/transactions/取引1のID/invoices/new` を開く
6. 「対象の注文書」の選択肢に **No.1 と No.2 の両方**が出ていることを確認
   （請書未返送の注文書は選択肢に出ない設計。No.2が請書を返す前は出ていなかったはず）

**合格条件**：請書を返す前はNo.2が請求対象に選べず、返した後は選べる。

## シナリオ4｜超過警告（最重要：拒否されないことを確認）

取引1のNo.1（¥1,860,000）には、シードの時点で ¥1,200,000 が入金済み。
ここにさらに ¥700,000 を請求すると合計 ¥1,900,000 となり、注文書の金額を ¥40,000 超える。

1. アカウントAで `/transactions/取引1のID/invoices/new` を開く
2. 「対象の注文書」で **No.1** を選ぶ
3. 「請求の根拠」で **任意** を選ぶ
4. 「請求額（税抜）」に **700000** と入力
5. 支払期日を適当に入力（例：翌月末の日付）
6. 「この内容で請求する」→確認モーダルが出る → **送信ボタンが押せる状態であること**
   （グレーアウトして押せない・エラーで弾かれる、なら不合格）
7. 送信する
8. **画面遷移せず、その場に「注文書の金額を ¥40,000 超えて請求しています」という警告が表示されること**
   （警告を読む前に取引詳細へ飛ばされる、なら不合格）
9. 「取引に戻る」を押して `/transactions/取引1のID` に戻る
10. 請求一覧に今回作った請求（¥770,000＝税込）が **提出済として実際に登録されている**ことを確認

**合格条件**：
- 送信ボタンが押せる（拒否されない）
- 警告メッセージが実際に表示される（消えずに読める）
- それでも請求は正常に作成されている

## シナリオ5｜人工精算（丸和塗装アカウントで検証）

取引3（浦安 事務所ビル 内装・応援）は 高橋工業が発注側、**丸和塗装が受注側**。
請求書を作れるのは受注側だけなので、**アカウントC（丸和塗装）**で検証する。

1. アカウントCでログイン → `/transactions` → 取引3（浦安 事務所ビル 内装）を開く
2. 「+ 請求書を作る」→ `/transactions/取引3のID/invoices/new`
3. 「対象の注文書」で No.1（人工契約）を選ぶ
4. 「請求の根拠」で **人工精算** を選ぶ
5. 「対象月」で **2026-08** を選ぶ
6. 画面に「延べ 8 人工 × ¥22,000 = ¥176,000」と表示されることを確認
   （シードの日報：8/20=2人・8/21=3人・8/25=3人 の合計8人工）
7. 支払期日を入力して送信

**合格条件**：延べ人工数と請求額が自動計算どおり（8人工・¥176,000）になっている。
