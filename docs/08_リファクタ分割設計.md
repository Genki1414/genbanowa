# ⑧ プロトタイプのリファクタ・分割設計 v1

現在のプロトタイプは単一ファイルで約4,000行。プロトタイプとしては正しい形だが、
本番実装に持っていく前に、どう分けるかを決めておく。

---

## 0. 現状の問題

| 問題 | 影響 |
|---|---|
| 1ファイル4,000行 | どこを触っても全体に影響する不安がある |
| 全画面が `App` の中の関数 | 状態が全部 `App` に集中（useState が40個以上） |
| 状態が画面遷移とデータで混在 | どれが「今どこにいるか」でどれが「データ」か分からない |
| 権限・プラン制限がUIに直書き | 同じ判定が何箇所にも散っている |
| ドメインロジックがUIに埋まっている | テストが書けない |

**特に深刻なのは4つ目**。`L.docs` や `canMsg()` の判定がUIコンポーネントの中に
散らばっているので、権限設計（④）を入れるときに全部を探し直すことになる。

## 2. 状態の整理

現在 `App` にある40個以上の `useState` を3つに分類する。

### ① サーバー状態 → 消える

`jobs` `akis` `txs` `threads` `invites` `companies` `partners` `photos` `sites`
`payments` `issued`

本番では**すべてサーバーから取得**する。React の state には持たない。
Server Components で取得し、更新は Server Actions → `revalidatePath`。

### ② URL状態 → ルーティングへ

`tab` `docTab` `feed` `jobOpen` `msgJob` `txOpen` `company` `siteOpen` `koushuOpen`
`folder` `inviteOpen` `scoutJob` `appsJob` `payOpen` `docView` `plansOpen` `partnerNew`
`postOpen` `akiPost` `siteNew` `txForm` `compose`

**全部URLにする。** 現在の「どの画面か」を state で持っているのが、
`clearNav()` のようなリセット関数が必要になっている原因。

```
/jobs                          案件一覧
/jobs?feed=aki                 空き情報
/jobs/[id]                     案件詳細
/jobs/[id]/applications        応募一覧
/jobs/new                      案件投稿
/firms                         会社一覧
/firms/[id]                    会社ページ

/messages/[convId]             やり取り

/transactions/[id]             取引詳細
/transactions/[id]/orders/new  注文書
/transactions/[id]/reports/new 日報

/transactions/[id]/documents/[docId] 書類の内容
```

**これで戻るボタンが正しく動く。**
今のプロトタイプはブラウザバックが効かないが、URL化すれば自然に解決する。

### ③ 純粋なUI状態 → ローカルに残す

`confirm` `toast` `cam` `baseImg`

## 3. プラン制限と権限の切り出し

**現状**：`L.docs ? ... : goPlan()` のような判定がUIに30箇所以上散在。

**あるべき形**：

```ts
// domain/plan/Quota.ts
export type QuotaKey =
  | "job.detail" | "conversation.start" | "scout.send"
  | "job.post" | "availability.slot" | "site.slot" | "document.issue";

export function checkQuota(
  plan: Plan, usage: Usage, key: QuotaKey
): { ok: true } | { ok: false; reason: string; limit: number | "unlimited" } {
  // ...
}

// domain/auth/Permission.ts
export type Action =
  | "order.issue" | "order.accept" | "invoice.submit" | "invoice.approve"
  | "payment.register" | "receipt.confirm" | "report.write"
  | "amount.view" | "user.manage" | "plan.change" | ...;

export function can(role: Role, action: Action): boolean { /* ... */ }
```

UI側は判定結果だけを受け取る。

```tsx
// components/ui/Gate.tsx
<Gate quota="document.issue" fallback={<PlanUpsell target="std" />}>
  <Btn onClick={submit}>注文書を送信する</Btn>
</Gate>

<Gate permission="amount.view">
  <Row label="請負代金" value={yen(order.amount)} />
</Gate>
```

**この形にしておくと、④の権限設計をそのまま乗せられる。**
今のままだと、`field` ロールの金額秘匿を入れるときに30箇所探すことになる。

## 4. 取引の状態遷移をドメインに閉じる

**現状**：`patchTx(tx.id, x => ({...x, invoices: ...}))` のように、
UI側が直接オブジェクトを組み替えている。

**あるべき形**：

```ts
// domain/transaction/Transaction.ts
export class Transaction {
  acceptOrder(orderId: string, by: Role): Result<Transaction>;
  rejectOrder(orderId: string, note: string, by: Role): Result<Transaction>;
  addOrder(input: OrderInput, by: Role): Result<Transaction>;
  requestAdditionalOrder(input: RequestInput, by: Role): Result<Transaction>;
  addReport(input: ReportInput, by: Role): Result<Transaction>;
  submitInvoice(input: InvoiceInput, by: Role): Result<Transaction>;
  approveInvoice(invoiceId: string, by: Role): Result<Transaction>;
  registerPayment(invoiceId: string, by: Role): Result<Transaction>;
  confirmReceipt(invoiceId: string, on: Date, by: Role): Result<Transaction>;
  requestCompletion(by: Role): Result<Transaction>;
  approveCompletion(by: Role): Result<Transaction>;

  availableActions(role: Role): Action[];   // ← UIのボタンはこれだけを見る
  overAmount(orderId: string): number;      // 超過判定
}
```

**`availableActions()` が単一の真実**という既存プラットフォームの原則を、
そのまま本アプリでも守る。UIは「何ができるか」を自分で判断しない。

これでテストが書ける。

```ts

```

## 5. デザイントークンの固定

```ts
// styles/tokens.ts
export const C = {
  sumi:   "#14171C",
  kami:   "#FFFFFF",
  yojo:   "#E9EDEA",
  keisen: "#D6DBD7",
  ki:     "#F5C518",
  midori: "#00874A",
  aka:    "#D22630",
  usu:    "#6B7280",
} as const;

// 意味づけを固定する（⑦の凡例と一致させる）
export const TONE = {
  actionRequired: C.aka,     // あなたの対応待ち
  inProgress:     C.ki,      // 進行中
  done:           C.midori,  // 完了・良好
  inactive:       C.usu,     // 終了・停止
} as const;
```

**色の意味を1箇所に集める。** 今は「緑＝完了」と「緑＝自社」と「緑＝信用が高い」が
混在している。凡例を出しても、実装が揺れていると意味がない。

## 6. 移行の順番

| 段階 | 内容 | 効果 |
|---|---|---|
| **1** | `styles/tokens.ts` と `components/ui/` を切り出す | 見た目の部品が再利用できる |
| **2** | `domain/plan/` `domain/auth/` を切り出す | 権限設計を乗せられる |
| **3** | `domain/transaction/` を切り出し、テストを書く | 状態遷移が保証される |
| **4** | ルーティングをURL化する | 戻るボタンが効く |
| **5** | サーバー状態を Supabase に置き換える | 本番 |

**1と2は今のプロトタイプのままでもできる。**
先に2をやっておくと、④の権限設計を検証しながら進められます。

3は本番実装と同時でよい（既存プラットフォームのドメイン層が土台にあるため）。

## 7. プロトタイプをどう扱うか

**捨てないこと。** 本番実装後も、
- 新機能の検討をまずプロトタイプで試す
- 顧客に見せて反応を見る

という用途で生き続けます。

ただし本番と乖離すると価値がなくなるので、
**`components/ui/` と `styles/tokens.ts` は本番と共有**するのがいい。
見た目の部品を共有しておけば、プロトタイプで試したものがそのまま本番に移せます。

---

## 8. 今すぐやるとしたら

優先度が高いのは**2（プラン制限と権限の切り出し）**です。

理由は、④の権限設計で `field` ロールの金額秘匿を入れる必要があり、
今の状態だと実装が散らばって必ず漏れるからです。
金額が現場に見えてしまう漏れは、**信用に関わる事故**になります。

`checkQuota()` と `can()` の2つの関数を作って、
UIの判定を全部そこに寄せるだけで、後の作業がかなり楽になります。
